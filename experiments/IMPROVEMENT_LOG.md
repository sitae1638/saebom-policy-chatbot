## v2 — 사전 트리거 오타 허용 매칭 (2026-11-02)
**무엇을 바꿨나**
- `synonyms.py`의 `fuzzy_hit()`: 한글을 자모(초성·중성·종성)로 풀어 편집 거리 1 이내면 같은 말로 인정
  - 예: 잃어바렸어 → "잃어버" 인정, 그마두는 → "그만두" 인정
- 이웃 글자 맞바꿈도 인정 (택비시 → "택시비")
- 사전에 "택시비" 트리거 1개 추가

**시행착오 (오탐 줄이기)** — 기준: 오타가 없는 변형 300문장에서 오타 허용으로 걸린 건수(=전부 오탐)
| 시도 | 내용 | 오탐 | 오타 문장 매칭 |
|---|---|---|---|
| 1차 | 자모 단위로 질문 전체를 훑음 (글자 경계 무시) | 270건 내외 | - |
| 2차 | 음절 단위로 창 맞춤, 2글자 단어는 초성 일치 조건 | 48 | 83 |
| 3차 | 2차 + 규정 문서에 실제 있는 말은 오타로 안 봄 | 42 | 79 |
| 4차 | 2글자 단어는 오타 허용 제외 | 7 | 31 |
| 최종 | 4차 + 조사·어미 붙은 표현 제외(사려면, 더 일하 등) | **0** | 25 |
- 원인: 두 글자 단어는 한 글자만 달라도 다른 정상 단어가 됨 (안내↔아내, 주당↔주차, 강의↔간의)
- 결론: "짧은 말은 오타 허용하지 않는다"가 가장 효과적인 규칙

**결과 (v1 대비)**
| 방식 | 오타300 | 새로 맞힘 | 새로 틀림 |
|---|---|---|---|
| 키워드 | 280 → 288 | 8 | 0 |
| 임베딩 | 286 → 289 | 3 | 0 |
| 하이브리드 | 293 → 296 | 3 | 0 |
- 변형 300 점수는 그대로 → 오탐 0건과 일치 (깨끗한 문장에는 영향 없음)

**남은 실패 (하이브리드 5개)**
| 문항 | 원인 | 대응 후보 |
|---|---|---|
| T076 야그밥겂 / T081 탯시 | 2글자 단어 오타 → v2에서 의도적으로 제외한 범위 | 규정 문서 단어 사전으로 질문 자체를 교정(오타 보정 단계) |
| T001 기기본 싀간 | 사전과 무관한 일반 단어(시간)의 오타 | 위와 동일 |
| P243 / T243 "10/1에 결제한 비용" | '결제한 비용'이 정산 규정 용어와 연결 안 됨, 날짜 표기 | 사전 보강 또는 재순위화 |

**한계·주의**
- 오탐 0은 이 600문항 기준. 새 질문에서는 다시 확인 필요
- 2글자 오타(탯시, 밥겂)는 일부러 포기한 영역 → 다음 단계에서 다른 방식으로 접근

**다음 단계 후보**
- v3: 질문 오타 보정 — 질문 단어를 규정 문서·사전 단어 목록과 비교해 고쳐 쓰기 (2글자는 "목록에 없는 말일 때만" 교정)
- 이후: 잡음 조항 감점, 검색 개수 늘리기·질문 분해, 재순위화
- 별도: 사전 작성에 쓰지 않은 검증용 질문으로 과적합 점검

## 검증셋 도입 (2026-11-02)
**만든 것**: `make_holdout.py` → `holdout_questions.csv`
| 분류 | 수 | 내용 |
|---|---|---|

| T 자연오타 | 10 | 사람이 실제로 치는 오타 (되요, 몇일, 어떻해, 식데) |
| O 범위밖 | 12 | 규정에 없는 내용 (복지포인트, 퇴직금 등) — 이후 "답변 거절" 단계용, Hit 점수에는 미포함 |
- 정답 문구가 해당 조항 본문에 실제로 있는지 스크립트로 자동 검증 (112문항 통과)
- `evaluate_holdout.py`는 화면에 집계만 출력 → 개별 실패를 보고 규칙을 맞추는 것을 방지

**측정 결과와 해석**
- 개발셋 99.2% vs 검증셋 89% (하이브리드 v2) → **약 10%p 과적합**. 사전이 개발셋 실패를 보고 만들어졌기 때문
- 그래도 사전(v1)은 처음 보는 질문에서도 +2~3점 효과 → 일반화되는 부분이 있음
- v2(오타 허용)는 검증셋에서 효과 없음, 키워드 방식은 오히려 84→82 하락 → 처음 보는 문장에서 오타 허용이 엉뚱하게 걸린 것으로 추정
- 검증셋에서는 **임베딩 단독(92)이 하이브리드(89)보다 높음** — 개발셋 결과와 반대. 기본 검색 방식 결정은 검증셋 기준이 맞음
- 가장 약한 영역: N 새조항 (사전이 다루지 않는 조항) → 사전처럼 "예시를 보고 만드는" 개선보다 **조항 전체에 고르게 작동하는 개선**이 필요

**앞으로의 원칙**
1. 개선 아이디어는 개발셋(600)에서 찾고 검증
2. 검증셋은 단계마다 1회 측정만, 개별 문항은 보지 않음
3. 개발셋만 오르고 검증셋이 안 오르면 "과적합"으로 기록

## v4 — 조항 세분화 검색 (2026-11-02)
**무엇을 바꿨나** (`chatbot/granular.py`, 문서 구조만 이용·예시 질문 미사용)
- 조항 78개 → 검색 조각 247개
  - 표는 행마다 "열이름: 값" 문장으로 변환 (예: "출장규정 > 제4조(숙박비) > 구분: 해외, 지역: 미주·유럽, 1박 한도: 250,000원")
  - 번호 항목(1. 2. 3.)·문단은 각각 한 조각, 조항 전체도 한 조각으로 유지
  - 모든 조각 앞에 "문서명 > 조항명" 접두
- 조각 점수를 조항으로 모아 순위를 매김 → 결과는 기존처럼 조항 단위

**시행착오**
| 시도 | 조항 점수 계산 | 개발600 (키워드/임베딩/하이브리드) | 새로 틀림 |
|---|---|---|---|
| 1차 | 가장 높은 조각 점수 | 588 / 594 / 597 | 1 / 2 / 2 |
| 최종 | 0.5×최고 조각 + 0.5×조항 전체 | 590 / 593 / 598 | 0 / 1 / 2 |
- 1차 문제: 조각이 많은 조항이 "최고 점수" 경쟁에서 유리해짐 → 한 문단짜리 "제2조(정규 근무시간)"가 조각 많은 "제3조(시차출퇴근)"에 밀림
- 비율 0.5는 미리 정한 값 (여러 값을 시험해서 고르면 개발셋에 맞추는 것이 되므로 하지 않음)

**해석**
- v1 이후 처음으로 **검증셋이 확실히 오른 개선** → 예시 질문 없이 문서 구조만 쓴 개선이 일반화됨
- 임베딩이 가장 큰 수혜: 긴 조항을 통째로 벡터 하나로 만들면 뜻이 흐려지는데, 조각으로 나누니 질문과 정확한 줄이 직접 비교됨
- 남은 문제: 한 문단짜리 조항이 여전히 불리한 경우 있음 (개발셋 P003 "하루 업무 시간")

**결정**
- 화면 기본 검색 방식: 하이브리드 → **임베딩**으로 변경 (검증셋 95 vs 91)

## v5 — 규정 밖 질문 처리 (2026-11-02)
**1차: 단일 기준 거절** (`chatbot/scope_guard.py`, `evaluate_scope.py`)
- 거절 규칙: ① 가장 가까운 조항의 임베딩 점수가 문턱값 미만 ② 가장 가까운 조항이 REG-00 제6조(규정에 없는 사항)
- 문턱값 결정 규칙(사전에 정함): 개발셋 정상 질문 점수 하위 1% → 0.8416
- 개발용 범위 밖 질문 40개 새로 작성 (`oos_dev_questions.csv`, 검증셋 범위 밖 12문항과 주제 겹치지 않게)
- 검증셋 범위 밖 12문항은 기준 결정에 쓰지 않음

**점수 분포 (임베딩·v4, 가장 가까운 조항 점수)**
| 구분 | 최저 | 하위1% | 중간값 | 상위5% | 최고 |
|---|---|---|---|---|---|
| 정상 질문 588 | 0.830 | 0.842 | 0.890 | - | - |
| 범위 밖 52 | 0.784 | - | 0.839 | 0.883 | 0.889 |
- 두 분포가 크게 겹침 → 점수 하나로 완벽히 구분할 수 없음

**결과**
| 평가셋 | 정상 오거절 | 범위 밖 거절 |
|---|---|---|
| 개발 (기준 결정에 사용) | 6/588 (1.0%) | 39/52 (75.0%) |
| 검증 (1회 측정) | **10/100 (10.0%)** | 9/12 (75.0%) |

**해석**
- 개발셋에서 1%였던 오거절이 검증셋에서 10% → 개발셋 질문이 규정 문장과 표현이 가까워 점수가 높게 나오는 편향
- 범위 밖 거절률(75%)은 두 셋에서 같음 → 범위 밖 판정은 일반화되지만, 정상 질문 쪽 기준이 너무 엄격
- 개발셋 실패 사례: 정상인데 거절된 6개는 모두 심한 오타 문장, 통과된 범위 밖 질문은 "근로계약서", "사원증 재발급", "경력증명서"처럼 규정 단어(계약서, 분실, 퇴사)와 겹치는 질문

**사용자 결정: 3단계 응답으로 변경**
| 단계 | 조건 | 화면 |
|---|---|---|
| 답변 | 점수 ≥ 0.8416 | 근거 조항 + 답변 |
| 확인 필요 | 0.8300 ≤ 점수 < 0.8416 | "정확히 일치하는 규정을 찾지 못함" 경고 + 관련 조항 + 문의처 |
| 거절 | 점수 < 0.8300 또는 REG-00 제6조 | 문의처 안내, 가장 가까운 조항은 접어서 참고로만 |
- LOW(0.8300) 결정 규칙(사전에 정함): 개발셋 정상 질문의 최저 점수(0.8301) → 정상 질문이 한 번도 내려간 적 없는 점수대만 거절
- 거절된 질문은 답변 생성(LLM)을 호출하지 않음

**결과 (3단계)**
| 평가셋 | 구분 | 답변 | 확인 필요 | 거절 |
|---|---|---|---|---|
| 개발 | 정상 588 | 582 | 6 | **0** |
| 개발 | 범위 밖 52 | 13 | 8 | 31 |
| 검증 | 정상 100 | 90 | 4 | **6** |
| 검증 | 범위 밖 12 | 3 | 3 | 6 |

- 정상 질문 잘못 거절: 검증셋 10% → **6%** (단일 기준 대비 감소), 나머지 4건은 "확인 필요"로 조항을 보여줌
- 범위 밖 질문: 12개 중 9개(75%)가 거절 또는 확인 필요로 처리, 3개는 그대로 답변으로 통과
- **덤으로 확인된 효과** (검증셋 정상 100, 집계만): 검색이 틀린 5건 중 3건이 '확인 필요/거절'로 걸러짐
  → "답변" 단계의 검색 정답률 88/90 = **97.8%**, 즉 자신 있게 답한 경우의 정확도가 올라감

**한계**
- 점수 하나로 판단하므로 규정 단어와 겹치는 범위 밖 질문(근로계약서, 사원증 재발급, 경력증명서)은 통과됨
- 개발셋 "연봉 인상률" 질문 일부는 연차 조항이 더 가깝게 나와 통과 (동의어 사전이 붙인 '급여 연봉' 용어보다 '올해·얼마나'가 연차 조항과 더 비슷하게 계산됨)
- 범위 밖 통과 건은 답변 생성 단계의 지시문("근거에 없으면 추측하지 말 것")이 2차 방어
- 기준값은 임베딩+v4 전용. 검색 방식이나 단계를 바꾸면 거절 기능은 꺼짐(항상 '답변') → 다시 측정 필요

**정리: 최종 구성 (현재 기본값)**
- 검색: 임베딩 + v4 (동의어 사전 + 오타 처리 + 조항 세분화)
- 응답: 3단계 (답변 / 확인 필요 / 거절)
- 검증셋: 검색 정답률 95%, 정상 질문 잘못 거절 6%, 범위 밖 처리 75%
